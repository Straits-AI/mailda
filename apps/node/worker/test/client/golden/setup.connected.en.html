4. Sending

Onboarding a domain for sending tells Cloudflare this account may send as it. It is separate from receiving, and a domain can have one without the other.

mail.example.com

Already covered by example.com, which is onboarded. This name itself is not, so it stops being covered if that one is removed.

Would create: TXT cf-bounce.mail.example.com, MX cf-bounce.mail.example.com

Leaves behind, and this Node cannot remove it: the DKIM record cf2024-1._domainkey.mail.example.com

5. Delivery outcomes

A sending domain reports what happened to each message — accepted (Cloudflare's delivered), bounced, complained — only if a subscription publishes those events into this Node's queue. Without one, every send stays unobserved. The domain must be onboarded for sending first.

mail.example.com

Carried by example.com, the onboarded domain that covers this name; the subscription is made for that one.

Nothing reads mailda-sending-events yet — events would sit unobserved. Subscribing attaches this Node as its consumer.
