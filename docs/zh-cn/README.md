# 淼达

知道谁回复过的共享收件箱。

两个人回复了同一位客户。没人说得清 `invoices@` 有没有被回复过。所谓共享收件箱，就是一个四个人都知道密码的 Gmail 账户。淼达把一个邮件地址变成受管控的工作：分派、冲突检测、工单、审批、审计记录，以及确定性的自动化。AI 只出现在你放置它的地方。

它运行在**你自己的 Cloudflare 账户**中。域名、邮件、加密密钥、模型密钥和账单都归你所有。没有淼达服务，没有许可证服务器，也没有遥测。断开与淼达的一切联系，什么都不会停止工作。

[mailda.site](https://mailda.site) 就是这份 README、`AGENTS.md`、`docs/` 和测量记录渲染出来的网站。它的首页是下面的状态表，排成一份 `mailda doctor` 报告的样子。网站上的内容没有一句写在别处，全都写在这里。

## 安装

一条命令，适用于 macOS、Linux、WSL 或 Git Bash：

```sh
curl -fsSL https://mailda.site/install.sh | bash
```

它会检查 git 和 Node 22，克隆本仓库，安装依赖，让你登录 Cloudflare；如果你有多个账户，会问用哪一个；问节点叫什么名字（默认 `mailda`）；如果你想要，再问一个你自己的主机名（先从列表中选一个区域，再填标签；直接按 Enter 则保留 `<worker>.<account>.workers.dev`）。然后它部署 Worker 及其 D1、R2 和队列，挂上主机名，并应用数据库结构。接着在同一个终端里认领节点：由你选定第一位管理员的邮件地址和密码，十个恢复码只打印一次。然后它再问一个问题：本节点应在哪个域名接收邮件；它用你已经给过的同一次 Cloudflare 登录，在那个子域名上开启路由，把规则写入节点，为发信接入该域名，把投递事件订阅到节点的队列，并逐项读回核对。邮箱的第一个邮件地址只问 `@domain` 之前的部分；如果你登录所用的邮件地址就在这个域名上，并且没有它自己的 Email Routing 规则把它送往别处，默认就取那个邮件地址的本地部分。安装的最后一行会说明你用哪个邮件地址登录、邮件从哪个邮件地址发出。安装结束时，节点就在接收邮件了。不需要仪表板，不需要 API 令牌，也不需要 OAuth 客户端（[测量记录](../receipts/wrangler-login-reach.md)）。拒绝某个问题，节点自己的页面日后也能做同样的事。在问过你之前，你的账户中什么都不会改变。给节点一个它自己的 Cloudflare 凭据（在*配置*页面粘贴一次的 API 令牌）是可选的，只用于日后从浏览器修改这些配置；它所取代的 OAuth 客户端已经移除（[ADR 42](../../Mailda-Full-Engineering-Blueprint.md)，2026 年 9 月 26 日修订）。在克隆的仓库中，同样的操作是 `pnpm install && pnpm mailda install`；在没有 bash 的 Windows 上，在 PowerShell 中运行它。

**CLI 向 wrangler 要什么，以及怎么要。** 它通过 `wrangler auth token --json` 复用 wrangler 的登录，所以保存在操作系统钥匙串里、或某个 wrangler profile 下的登录都能用，令牌也从不出现在终端或 wrangler 自己的调试日志里。Global API Key（`CLOUDFLARE_API_KEY` 加 `CLOUDFLARE_EMAIL`）会被拒绝，因为 wrangler 会用它部署，而节点只接受 Bearer 令牌；请改为设置 `CLOUDFLARE_API_TOKEN`。它启动的每个 wrangler 都带着 `WRANGLER_SEND_METRICS=false` 运行，除非你自己设置了这个变量，因为 wrangler 默认会发送使用统计；wrangler 自己的 npm 更新检查没有关闭。它读取的应答都以 JSON 形式、在 wrangler 的默认日志级别下、不带颜色地请求，无论你的 shell 设置了什么 `WRANGLER_LOG` 或 `FORCE_COLOR`。它需要 wrangler 4.97 或更高版本（[测量记录](../receipts/workflow-provisioning.md)）；单就 JSON 应答而言，4.65 就已具备（[测量记录](../receipts/wrangler-json-output.md)）。

**安装之后。** 打开节点。在它有邮件地址、并且有邮件路由到它之前，它只显示下一步配置以及完成这一步的命令，别的什么都不显示；两者都具备之后，显示收件箱。如果节点在安装程序能为它做配置之前就已被认领，在克隆的仓库中运行 `pnpm mailda setup` 完成配置，它做同样的接收、发信和投递结果配置，但不部署。然后给你选定的邮件地址发一封邮件：它出现在收件箱里，这就是证明。

**添加成员。** 在*成员*页面，为对方的登录邮件地址签发一份邀请：链接只向你显示一次，不会通过邮件发出，你用自己信得过的任何方式交给对方，对方打开它并设定密码。在你于同一页面授予对方某个邮箱上的关系之前，对方什么都不持有；每种关系都写成它允许对方做什么。邀请时勾选*同时为对方建一个邮箱，邮件地址为*，即可用你域名上的一个邮件地址为对方建一个邮箱；和任何邮箱的创建者一样，它只授予你，对方在上面什么都不持有。一旦对方有了使用该邮件地址的账户，且在该邮箱上没有直接持有任何关系，*成员*页面会询问是否把它交给对方，并写明它授予的两种关系；对于你收回过对方关系的邮箱，它不会再问。那里的邮件地址输入框只填 `@` 之前的部分，你的域名显示在旁边。要在对方自己的邮件地址接收邮件，比如 `user1@example.com`，就把那个邮件地址加到对方持有的邮箱上（*成员* → *添加邮件地址*）；在 Catch-all 地址指向节点的域名上，不需要别的操作，除非该邮件地址有它自己的 Email Routing 规则把它送往别处或已被禁用，页面会指明这一点；在子域名上，节点会在同一操作中写入路由规则，如果写不了，会准确说明要运行什么。写邮件界面会显示邮件从哪个邮件地址发出：是邮箱的邮件地址，绝不是你登录所用的那个，读不到时也会如实说明。每个邮箱都在那里列出它的邮件地址，每个旁边都有*移除*：如果路由规则是本节点写的，规则随之移除（接管来的规则会保留，页面会指明如何恢复原样）；收到过邮件的邮件地址会保留，并写明名称，因为它名下的每封邮件都是经由那个邮件地址归入的。邮箱和团队也在同一页面改名。

同一条命令可以添加第二个节点，也可以重新部署已有的节点；更新是单独的命令（见下文），因为更新还要先拉取发布版本并备份节点。它会列出账户中已有的节点（每个节点都以自己的名称注册一个 `ButlerRun` Workflow），由你给出的名称决定：已有的名称会经由金丝雀升级，这需要一次节点的 URL，并记在被 git 忽略的 `.mailda/nodes.json` 中；新名称会在第一个节点旁再部署一个节点，所有资源都以这个名称命名。

[![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https://github.com/Straits-AI/mailda)

这个按钮不用终端就完成部署这一半：它创建 D1 和 R2，构建 Worker，不把任何 id 写进你的克隆；节点在被认领时自行应用数据库结构。之后你需要认领码，在克隆的仓库中运行 `pnpm mailda claim-secret` 即可打印出来。第一次点击得到的是一个无法使用的节点，当时发现并修复了什么，记在[测量记录](../receipts/deploy-button-install.md)中。

**有一步两条路径都替你做不了。** 投递结果（`accepted`、`bounced`，按收件人）经由队列到达，要观测它们，你的账户里需要两样东西：该队列上的一个消费者，以及一个发布到该队列的 `email.sending` 事件订阅。安装程序会挂上消费者。订阅在节点持有你账户的 API 令牌之后，从节点自己的配置页面创建（[`docs/cloudflare-settings.md`](../cloudflare-settings.md)）。两者都存在之前，每个收件人都停在 `unobserved`，`mailda doctor` 会指出缺的是哪一半，而不是让静默被读成“没有退信”（[测量记录](../receipts/queue-provisioning.md)）。

有一种情况任何订阅都解决不了：在测量过的那一个案例中，发往你自己账户中已验证的目标地址（为 Email Routing 转发而验证的地址）的邮件根本没有产生投递事件（[测量记录](../receipts/email-sending-events.md)，其中也记录了把它与 Cloudflare 以外的投递区分开的那次发信，以及这一结论只建立在一个已验证地址之上）。节点会读出它的收件人中哪些是这种地址（`mailda setup` 和 `mailda upgrade` 借用 wrangler 的登录，或在配置页面使用带有可选权限 Email Routing Addresses: Edit 的令牌），发件箱把它们标为 `verified destination`，`mailda doctor` 也不会把那种静默算作看不见。

**已经在路由邮件的域名。** 配置页面会列出你区域上的 Email Routing 规则，让你把其中一条指向节点。这会替换该邮件地址的去向（Cloudflare 每条规则只允许一个动作），原来的目的地会保留在审计记录中，并写进规则自己的名称，*恢复原样*可以还原它。每条规则都能改回去；在此期间到达这里的邮件留在这里。其他邮件地址已有的规则保持不动。

`mailda install`、`mailda setup` 和每次 `mailda upgrade` 结束时，都会针对节点接收邮件的名称列出同一份清单：每个有自己规则的邮件地址、它的去向，以及节点为它提供的那一项更改。以下是默认行为，以及如何更改每一项：

- **只有在可以提供某条规则时，才问一次 y/N。** 在你有意保留规则的区域上，每次升级都会问；不会记住“否”。回答 N，或带 `--yes` 运行。
- **每条规则默认“保持不动”。** 转发规则（通常是某人的私人邮箱）提供 *receive here only*（只在这里接收）：目的地不再收到任何邮件，从那里发出的回复在这里也看不到。指向另一个 Worker 的规则提供 *receive here*（在这里接收）：那个 Worker 不再接收该邮件地址，本节点也看不到它做了什么。丢弃规则提供 *receive here*：Cloudflare 原本丢弃的邮件从此被保留。转发规则还提供 *receive here and keep forwarding to X*（在这里接收并继续转发到 X，ADR 47）：节点先存储每封邮件，再把它转发到 X，即该规则自己的已验证目的地。转发出去的邮件在节点扫描之前就已离开，转发失败会显示在“成员”页面上而不会告诉发件人，Cloudflare 也不会报告发往 X 的投递情况。`mailda provider --forwards` 列出这些转发；`mailda provider --destinations [--addresses]` 和 `--add-destination <email>` 列出并登记账户的目标地址（新登记的地址会一直等待验证，直到那边有人点击 Cloudflare 的链接）。
- **副本默认关闭。** 保留转发的邮件地址可以选择启用副本（`mailda provider --copy <address> on`、“成员”页面，或 `--copy` 配合 `--forward keep`）：当 Cloudflare 以未验证为由拒绝转发时，邮件改由该邮件地址本身通过 Email Sending 发出。收件人看到它来自“Alice via <mailbox>”，回复会发给 Alice，正文是她写的原样；上限 5 MiB（`email.outbound.max_bytes`）；带有危险附件、已被隔离或未通过 DMARC 的邮件不会生成副本；每个副本都计入当天的发信量，并像任何一次发信一样出现在发件箱中，以开启副本的那位管理员的名义定稿。
- **转发只进入你选定的邮箱**：首先提供的是一个以该邮件地址命名的新邮箱（或已经以它命名的那个邮箱，绝不会再建第二个），绝不会默认放进唯一的那个邮箱（API 会拒绝，`E_ROUTING_FORWARD_NEEDS_MAILBOX`）。
- **节点不为其接收邮件的名称上的规则**（另一个子域名）只显示为一行计数，并附上用来列出它们的 `mailda provider --routing-rules <name>`。
- **`--yes` 或没有终端时，不更改任何规则**：它打印清单，并为每一项打印确切的 `mailda provider --take-over` 命令；凡是需要选择邮箱的地方，附上 `--mailbox <mailbox id>` 并列出各个邮箱；对转发规则，附上 `--forward stop`、`--forward keep` 和 `--forward keep --copy`；交互式步骤提供同样的三项，其中“保留转发并启用副本”一项用节点自己的一句话说明副本是什么。
- 已禁用的规则、有多个目的地的规则、重复的规则，以及开启了子地址的区域，都会连同原因一起列出，但从不提供更改。

**删除节点之前，把它接管的每条规则都恢复原样**（`mailda provider --routing-rules <domain>` 会列出每一条及其恢复方式）。如果节点已经不在了，从 2026 年 10 月 1 日起接管的规则会在自己的名称中记下原来的去向，`mailda provider --put-back <rule id> --domain <domain> --without-node` 会用你自己的 wrangler 登录把它恢复，不需要节点，也不留审计条目。有两类规则不在名称中记录任何东西，只能通过节点恢复，所以务必在删除节点之前完成：**Catch-all 地址**（接收步骤所做的接管），以及 2026 年 10 月 1 日之前接管的任何规则。对于名称读回来与写入时不一致的规则，这一步也会如实说明。在区域自己的名称上，接收步骤改为提供 **Catch-all 地址**：一条规则把该域名所有未匹配的邮件指向这里，原来的目标保留下来以便恢复原样，从此每个没有自己规则的邮件地址都在节点内的“成员”页面中管理。邮件地址自己的已启用规则优先于 Catch-all 地址（对已禁用的规则，Cloudflare 没有说明），所以 `mailda install`、`mailda setup`、`mailda provider --onboard-receiving` 和配置页面会在你做选择之前列出每个这样的邮件地址及其去向，并且从不更改这些规则；在子域名上 Cloudflare 只允许字面规则，所以在“成员”中添加邮件地址会在同一操作中写入它的规则。`mailda provider --routing-rules <domain>` 在 CLI 中做同样的事。配置页面和 CLI 只在节点确实会去做的地方提供接管或恢复原样：已禁用的规则、有多个目的地的规则、有多条规则的邮件地址，以及本节点从未接管过的规则，都会改为连同拒绝原因按名称列出；开启了子地址的区域会在你操作时被拒绝。已经在“成员”中的邮件地址保留它的邮箱，接管时会指明这一点。每次接管和恢复原样都会读回规则，当 Cloudflare 保存的内容与发送的不一致时会如实说明，包括应答丢失、意味着更改可能已经生效的情况。

**同一账户中的第二个节点。** 给安装程序一个新名称即可；在脚本中，`mailda deploy --name <worker>` 做同样的事。两者都会由这个名称派生出 Worker、Workflow 和其他所有资源，写入一个被 git 忽略的配置；首次安装测得用时 108 秒。

**更新已安装的节点**只需一条命令，在安装时留下的克隆目录中运行：

```sh
curl -fsSL https://mailda.site/update.sh | bash
```

它会转交给 `pnpm mailda upgrade`，在克隆的仓库中两者是一回事。它拉取发布用的远程仓库，克隆落后时快进合并并说明，重新安装依赖，账户中有多个节点时问是哪一个；然后在触碰数据库结构之前，先做一次 `mailda backup`，存入被 git 忽略的 `.mailda/backups/<node>/<time>` 目录，没有备份就拒绝继续。它按阶段列出每个待执行的迁移：*expand*（只做添加，对正在运行的版本安全）或 *contract*（删除或收窄，除非带 `--contract`，否则拒绝），只问一次，然后运行与 `mailda deploy` 相同的 expand、金丝雀、关卡、推广流程。从未配置过接收的节点，之后会被提供安装时的那一步配置，使用同一次登录。只要它能登录节点，就会接着用同一次登录读出节点的收件人中哪些是账户的已验证的目标地址，并打印数量；wrangler 不给它令牌时，它用 wrangler 的原话打印原因，然后继续。它从不创建节点；用已有名称运行 `mailda install` 同样会升级，但用的是克隆中现有的代码，这正是这个命令存在的原因。

按钮克隆时不带历史，也不带远程仓库。升级在第一次运行时处理这一点：它添加发布用的远程仓库，允许不相关的历史合并一次，并解决更新路径允许的唯一冲突 `package.json`：保留你的 Worker 的 `name`，其余一切取上游的。如果还有其他冲突，它会中止合并并列出文件名，因为那是有人改过的克隆。保证 `package.json` 是唯一冲突文件的是 `test/node/update-path.test.ts`；同样的步骤手动执行是：

```sh
git remote add upstream https://github.com/Straits-AI/mailda.git
git fetch upstream main
git merge upstream/main --allow-unrelated-histories
# One conflict, in package.json. Keep your own `name`, take upstream's everything else.
```

**重置密码。** 产品中还没有修改密码的流程。`pnpm run set-password <email>` 在关闭回显的提示符下读取新密码，用与 Worker 相同的 PBKDF2 派生验证值，并吊销所有登录会话。它在 Worker 之外运行，所以不会出现在审计记录中。

## 状态：功能可用的 alpha 版，尚不能用于生产

**不要让它成为你在意的邮件的唯一一份。** 它能接收、存储、阅读、回复、管控和自动化，但它为自己设定的发布关卡尚未全部通过。

| **恢复已成功三次，其中一次一直做到接收邮件** | 三次演练（#92）：跨账户恢复，然后是一次真实备份，然后是同账户恢复，它接管了一个域名，写入了自己的路由，并接收了一封来自外部的邮件。目录数据库的导入速度约为每秒一千行。证据的复制可以用任何能搬运字节的工具完成，包括会丢掉密钥标签的工具，目前只用 wrangler 计时过（每个对象 5.4 秒）；真实邮箱应当用存储桶到存储桶的复制，这里有意没有计时。[操作手册](../disaster-recovery.md)。 |
| **部署会自行推广，已测量两次** | `mailda deploy` 用金丝雀执行 expand/contract，若新版本的 `doctor` 比现任版本差，就拒绝推广（#98）。金丝雀通过生产主机名上的版本覆盖访问，因为带 Durable Objects 的 Worker 没有预览 URL。在免费账户上未测量，而 ADR 25 本来就说不要在免费账户上运行。[测量记录](../receipts/deploy-drill-live-account.md)。 |
| **邮件安全还很薄弱** | 接收服务器给出的 SPF、DKIM 和 DMARC 判定会被存储；DMARC 未通过会显示在邮件上和列表中它的那一行，完整判定在邮件详情中点一下即可看到。附件按文件名和魔数判断，链接按其真正的去向判断；邮箱可以把发件人域名不认可的邮件、或带危险附件的邮件隔离下来。硬退信的收件人在定稿时会被拒绝，直到有管理员为它作保。发信规则可以暂留、加关卡或拒绝对 DMARC 未通过邮件的回复，伪造发票正是在这一步造成损害。你在自己账户中运行的分类器可以通过 API 隔离一次投递，并附上原因和分数；节点本身不附带任何分类器（[示例](../../examples/hold-agent/)）。ZIP 只列出内容而不打开，列出程序的 ZIP 会被隔离。发出时，程序、脚本、以文档名义伪装的程序，或列出这类文件的 ZIP 会被拒绝，除非作者坚持发送（源代码的 zip 是常见情况），写邮件界面会给出警告，定稿的审计条目按位置记录放行了哪些附件。邮箱可以限制收发附件的大小和类型。尚缺：隔离开关之外的入站处置、RAR 和 7z 的内容列表，以及任何分类器，因为 Workers AI 没有用于邮件的分类器（[测量记录](../receipts/workers-ai-classifier.md)）。[`docs/mail-security.md`](../mail-security.md)。 |
| **英文与简体中文** | 界面文字是每种语言一份的类型化词表（ADR 46）：缺少译文就无法编译；另有一项用 TypeScript 类型检查器做的检查，逐个文件统计尚未进入词表的字符串，要降到零，现在已经是零。自 2026 年 10 月 2 日起，简体中文（标志为淼达）与英文并列提供：浏览器请求 `zh`、`zh-CN`、`zh-SG` 或 `zh-MY` 时得到简体中文（繁体的 `zh-TW`、`zh-HK` 和 `zh-MO` 不会），设置 > 语言以及登录前的切换开关都可以选择任一种，`?locale=` 可以为单次页面加载指定一种。每个页面都已迁移，包括登录前的页面；用伪语言渲染每个路由及其错误状态，没有发现任何裸露的英文；词汇表中的每个词都经仓库所有者确认，最后一层的 25 个词在 2026 年 10 月 2 日的工作会议上按提议接受，没有经过审阅页面。无论界面是什么语言，邮件都按它自己文字的字形显示，依据先是它的字符集，再是它的 `Content-Language`。API、CLI 供机器读取的输出、doctor 的文本、MCP 和 SDK 永远保持英文，为的是解析它们的程序。[`docs/i18n.md`](../i18n.md)。 |

它现在适合：设计合作伙伴的 alpha 试用、一个非关键的共享邮箱，以及试用管控和确定性自动化模型，这部分比这里的其他任何部分都更成熟。
